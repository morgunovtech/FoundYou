# Service worker для Found You — задачи, корнер-кейсы и чем за это платим

Отдельный проект, а не пункт бэклога: фича выглядит как «добавить один файл», а на деле это
постоянное состояние на чужом устройстве, которое мы не можем ни посмотреть, ни сбросить.
Этот файл — то, что нужно решить **до** первой строки кода.

Решение от 2026-09-20: пока service worker не сделан, `display` в `public/manifest.json`
переключён на `browser`. Ярлык на рабочем столе больше не притворяется приложением, которое
работает без сети.

## Зачем это вообще

Четыре разные выгоды, и стоит различать их — потому что цена у них общая, а ценность разная.

1. **Повторный визит без 60 МБ.** Сейчас всё раздаётся с `Cache-Control: max-age=86400`, то
   есть кэш живёт сутки. Через двое суток человек качает всё заново. Реальные размеры на
   2026-09-20 (`du` по `public/`):

   | Что | Размер | Когда качается |
   |---|---|---|
   | `mediapipe/wasm/vision_wasm_internal.wasm` | 11,8 МБ | при первой детекции |
   | `mediapipe/wasm/vision_wasm_nosimd_internal.wasm` | 11,0 МБ | только без SIMD |
   | `mediapipe/models/efficientdet_lite2.tflite` | 12,1 МБ | при первой детекции |
   | `mediapipe/models/blaze_face_full_range.tflite` | 1,1 МБ | при первой детекции |
   | `mediapipe/models/blaze_face_short_range.tflite` | 0,2 МБ | при первой детекции |
   | `ocr/tesseract-core-*-lstm.wasm.js` (три варианта) | по ~3,9 МБ | один из трёх, по возможностям |
   | `ocr/lang/rus.traineddata.gz` + `eng.traineddata.gz` | 5,6 МБ | при первом OCR |
   | `c2pa/*` | 6,0 МБ | только если в файле есть манифест |

   То есть типовой первый разбор фотографии — это примерно **33 МБ** (wasm + efficientdet +
   два blazeface + один tesseract core + два языка), а не «20 МБ», как записано в старых
   заметках. Весь каталог `public/ocr` + `public/mediapipe` + `public/c2pa` — 59 МБ.

2. **Офлайн.** Открыл, выключил интернет, разобрал фото. Это единственное доказательство
   обещания «снимок не покидает устройство», которое человек может проверить сам, не открывая
   вкладку «Сеть» и не читая код.

3. **Web Share Target** — «Поделиться → Found You» прямо из галереи телефона. Без service
   worker технически невозможно: цель шаринга принимает POST с файлом, и перехватывает его
   именно worker.

4. **Ярлык-приложение** (`display: standalone`) перестаёт врать.

## Что решить до кода

### 1. Инвалидация моделей при деплое — главный корнер-кейс

Код и стили versioned по имени (`/assets/*` с хэшем, `immutable`), а модели — нет:
`/mediapipe/models/efficientdet_lite2.tflite` называется так всегда. Если worker закэширует
его навсегда, то при смене модели человек останется на старой **без единого признака** — ни
ошибки, ни другого результата, просто другие рамки, чем у всех.

Варианты:

- **Хэш в имени при `prepare:assets`.** Скрипт кладёт `efficientdet_lite2.<sha8>.tflite` и
  пишет манифест `public/mediapipe/manifest.json`, который читает `useImageAnalysis`. Тогда
  модели становятся `immutable` честно, а старые версии вымываются по имени. Минус: трогаем
  `prepare:assets`, `_headers` и все места, где путь к модели захардкожен.
- **Версия кэша в имени Cache Storage** (`found-you-v<BUILD>`), и при активации нового worker
  старые кэши удаляются целиком. Проще, но значит: **каждый деплой = повторная закачка 33 МБ**.
  Для сервиса, который деплоится по нескольку раз в неделю, это хуже, чем нынешние сутки кэша.
- **Гибрид:** статика по версии сборки, модели по хэшу содержимого. Скорее всего это и нужно,
  но это уже два механизма.

Решить надо до кода, потому что от выбора зависит, трогаем ли мы `prepare:assets`.

### 2. Залипшая старая версия

Классическая жалоба на PWA: «у меня всё по-старому». Worker по умолчанию активируется только
когда закрыты все вкладки со старым. Нужно:

- версия сборки внутри worker (Vite `define`), чтобы он сам понимал, что устарел;
- `registration.update()` при загрузке страницы;
- явная плашка «вышла новая версия — обновить», а не тихий `skipWaiting()`: тихая подмена
  worker посреди разбора фотографии может подменить модель между двумя проходами детектора.

Отдельный вопрос: что делать, если человек в этот момент **в середине очистки**. Ответ по
умолчанию — не трогать, предлагать обновление только когда на странице нет загруженного файла.

### 3. iOS Safari чистит хранилище

Apple удаляет данные сайта (включая Cache Storage), если сайтом не пользовались **семь дней** —
для сайтов, не добавленных на домашний экран. Это надо проверить на реальном устройстве и
записать сюда с датой, а не принимать на веру: правило менялось и касается не всех хранилищ
одинаково. Практический вывод, если подтвердится: на iPhone обещание «второй визит без
закачки» верно только для тех, кто заходит чаще раза в неделю или поставил ярлык.
Для Android/Chrome такого правила нет, но есть вытеснение при нехватке места.

### 4. Сколько места мы занимаем на чужом телефоне

59 МБ, если кэшировать всё; ~33 МБ, если кэшировать только то, что реально используется на
этом устройстве (один вариант tesseract-core из трёх, wasm с SIMD или без). Нужно:

- решить, кэшируем ли `c2pa` (6 МБ) заранее или только по факту встречи манифеста — сейчас он
  грузится лениво и у большинства не грузится никогда;
- кэшировать **по факту запроса** (stale-while-revalidate на конкретный URL), а не списком в
  `install`: список гарантированно закачает и то, что этому браузеру не нужно;
- показать человеку, сколько занято, и дать кнопку «очистить кэш». Инструмент про приватность,
  который молча занимает 33 МБ, — плохая шутка.

### 5. CSP и `_headers`

`worker-src 'self' blob:` в CSP уже есть, отдельный хост не нужен, но:

- `/sw.js` должен отдаваться с `Cache-Control: no-cache`, иначе обновление worker будет
  приходить с суточной задержкой (это самая частая ошибка в этом месте);
- `Service-Worker-Allowed` не нужен, пока worker лежит в корне;
- Pages Functions (`/api/*`) worker **не должен** перехватывать: эти ответы кэширует Cloudflare
  по своим правилам, и своё кэширование поверх даст устаревшую погоду.

### 6. Что worker не должен делать никогда

- Не трогать `/api/*` (см. выше).
- Не кэшировать ничего, что связано с фотографией пользователя. Фото не проходит через
  сеть вообще, но правило стоит записать, чтобы оно не нарушилось в будущем при Web Share
  Target, где файл прилетает POST-ом.
- Не кэшировать тайлы OpenStreetMap: они и так идут мимо нас, а кэш тайлов — это уже история
  перемещений на устройстве.

### 7. Как это ломается в разработке

`npm run dev` с активным worker — источник часовых отладок «почему правка не видна».
Нужно: не регистрировать worker в dev (`import.meta.env.PROD`), и в README — строчка о том,
как его вычистить (`chrome://serviceworker-internals`, Safari → «Очистить данные сайта»).

## Порядок работ, если решаемся

1. Решить вопрос 1 (инвалидация моделей) — это развилка, от которой зависит всё остальное.
2. `prepare:assets` кладёт хэш в имена моделей и пишет манифест; точки чтения переводятся на него.
3. `sw.js`: precache только оболочки (HTML, `assets/*`, `ds/v1/*`, шрифты), остальное —
   stale-while-revalidate по факту запроса; `/api/*` не перехватывается.
4. Плашка «вышла новая версия» + `registration.update()` на загрузке.
5. Экран «Кэш: N МБ» с кнопкой очистки.
6. Проверка на реальном iPhone и реальном Android: офлайн-разбор, обновление версии, поведение
   после недели без визита.
7. Только после этого — возвращать `display: standalone` и браться за Web Share Target.

## Чем платим (коротко, для решения)

| Плюс | Минус |
|---|---|
| Второй визит мгновенный, без 33 МБ | 33–59 МБ постоянно заняты на устройстве |
| Работает офлайн — доказательство приватности | Риск залипшей версии, если ошибёмся в инвалидации |
| Ярлык перестаёт врать | Отладка усложняется, жалобы «у меня старое» |
| Открывает Web Share Target | На iPhone кэш всё равно не вечный (п. 3) |
